Executive summary

TelePoint is a multi-tenant EMI (instalment-lending) portal. Retailers sell phones on instalments, register customers, and collect monthly payments; a super admin approves those collections, manages fines, settles accounts and runs reports. The whole product rests on one boundary: retailer A must never see or touch retailer B's book, and only the super admin may approve money movements.

Both halves of that boundary were breachable.

The application's own API routes are, with three exceptions, carefully written — most check the session, resolve the caller's role from the database, and re-derive the retailer scope server-side rather than trusting a query parameter. The failures were concentrated one layer down, in the PostgreSQL grant model, where the protections were assumed rather than enforced.

PostgreSQL grants EXECUTE on every new function to PUBLIC by default. The schema carefully grants its privileged functions TO service_role — but never revokes the implicit PUBLIC grant that is already there. The intended restriction therefore never took effect. Because approve_payment_request() is SECURITY DEFINER and performs no caller check at all — it simply trusts the p_admin_id it is handed — a retailer could call it straight from the browser with the public anon key and approve their own pending collection.

The same default exposed the fine engine and EMI-schedule generator, and left get_due_breakdown() readable for any customer id by any logged-in retailer.

Separately, three report endpoints — none of them linked from the UI, which is precisely why they had gone unreviewed — checked only that a session existed, with no role check and no retailer scoping, and returned the entire portfolio.

Every finding below was reproduced against a real PostgreSQL instance loaded with the actual portal schema before being fixed, and re-tested afterwards. No EMI, fine, payment, settlement, completion or NPA calculation was altered.

Actors found in the code: anonymous visitor; customer (no login — identifies with Aadhaar or mobile via /api/customer-login, or a persistent app token); retailer (profiles.role = 'retailer', owns a row in retailers); super admin (profiles.role = 'super_admin'). The decisive structural fact is that boundary 1 and boundary 4 are the same boundary. Findings in detail

The critical and high findings in full. Medium and low findings are summarised in the table above and in Remaining risks.

SEC-001Retailer can approve their own payment collections

CriticalRetailerFixed & verified
Location
approve_payment_request(UUID, UUID, TEXT) — defined in migrations/027_first_emi_charge_partial.sql, granted in every schema baseline.
Vulnerability
The function is SECURITY DEFINER and performs no caller identity check. It accepts p_admin_id as a parameter and writes it as the approver. The schema grants it TO service_role — but PostgreSQL had already granted EXECUTE to PUBLIC when the function was created, and nothing ever revoked that. There is no REVOKE statement anywhere in the repository.
Root cause
A grant was mistaken for a restriction. GRANT … TO service_role adds a privilege; it does not remove the default PUBLIC one. The intended "server-only" boundary therefore never existed.
Impact
A retailer holding only the public anon key and their own login could call supabase.rpc('approve_payment_request', …) from the browser and approve their own pending collection — marking EMIs paid, clearing fines and advancing customer completion without any super-admin involvement. The same call works against any other retailer's request id, and anon could reach it too.
Evidence
SELECT * INTO v_request FROM payment_requests WHERE id = p_request_id FOR UPDATE; — the function's first statement. There is no auth.uid(), no get_my_role(), and no ownership predicate anywhere in the body.
Minimal fix
REVOKE ALL … FROM PUBLIC, anon, authenticated and GRANT EXECUTE … TO service_role. The function body is untouched — the approval logic, the partial-payment maths and the fine handling are all unchanged. The app only ever calls this through the service-role client behind /api/payments/approve, which already verifies super_admin.
Business logic
NONE. Approval semantics are identical; only the caller set changed.
Regression test
SEC-001 and BYPASS-4/7 — retailer self-approval, cross-retailer approval and anonymous approval are all denied; BIZ-5/6 confirm the real admin path still approves and the EMI still flips to APPROVED.
Status
FIXED — VERIFIED (reproduced exploitable, then confirmed closed)

SEC-002 / SEC-003Whole-portfolio customer data downloadable by any retailer

CriticalRetailerFixed
Location
app/api/report/customer-profit/route.ts and app/api/report/fine-due/route.ts
Vulnerability
Both handlers stopped at if (!user) return 401. No role check, no retailer scoping, and both then query with the service-role client, which bypasses RLS entirely.
Root cause
Authentication was treated as authorization. Every sibling report resolves the caller's retailer id and filters on it; these two never did. Neither endpoint is referenced anywhere in the UI, so neither was exercised during normal review — the classic unlinked-route blind spot.
Impact
Any authenticated retailer issuing a single GET receives every customer of every retailer: full name, IMEI, mobile number, purchase value, disbursal, EMI terms, amounts collected, outstanding fines and per-customer profit. This is a complete competitor-facing book leak and a personal-data breach.
Evidence
const { data: customers } = await svc.from('customers').select('…, retailer:retailers(name)').order('customer_name'); — no .eq('retailer_id', …) anywhere in the file.
Minimal fix
Require super_admin, matching the existing /api/report/payment-collection convention. Chosen over retroactively adding retailer scoping because these are whole-portfolio aggregate reports with no retailer parameter, and no UI surface offers them to retailers — so requiring admin closes the hole without inventing new behaviour.
Business logic
NONE. Report contents, columns and figures are unchanged for the super admin, the only legitimate caller.
Regression test
Verified by inspection and production build; no automated HTTP harness exists in this repository.
Status
FIXED

SEC-006IDOR — any retailer can read any customer's dues

HighRetailerFixed & verified
Location
get_due_breakdown(UUID, INT) — called from the browser in app/admin/page.tsx, app/retailer/page.tsx and app/noc/[id]/page.tsx.
Vulnerability
SECURITY DEFINER (so RLS does not apply), granted to authenticated, and it accepts any p_customer_id with no ownership check.
Impact
Retailer A supplies retailer B's customer id and receives that customer's outstanding EMI, accrued fine, first-EMI charge, total payable and overdue state. Customer ids are visible in other responses, so this is directly chainable.
Minimal fix
The original body was renamed, not rewritten, to get_due_breakdown_impl, and a thin wrapper installed that only answers "may this caller ask about this customer?" before delegating. Super admin keeps access to every customer; a retailer is restricted to their own; service_role (the customer portal, which authenticates the customer itself) is unaffected; anon is denied outright. *_impl is revoked from PUBLIC/anon/authenticated so the wrapper cannot be side-stepped.
Business logic
NONE — proven. The function body is byte-for-byte the original. Output was captured before and after the change and diffed: identical.
Regression test
SEC-006, SEC-006b, BYPASS-1; BIZ-1/2/4 confirm retailer-own, admin-any and server-side access all still work.
Status
FIXED — VERIFIED

SEC-005Next.js middleware authorization bypass

HighAnonymousFixed
Location
package.json — next@14.2.16; boundary defined in middleware.ts.
Vulnerability
CVE-2025-29927 lets a caller skip middleware execution entirely with a crafted request header. This matters more here than in a typical app because middleware.ts is the role gate for /admin, /retailer and /noc. npm itself flags the installed version as vulnerable on install.
Impact
The session and role checks protecting the admin surface can be bypassed. Impact is bounded — the admin pages are client components whose data comes from API routes that re-check authorization, and /noc re-checks super_admin server-side — but the app's stated boundary is defeated.
Minimal fix
Upgraded to next@14.2.35, the latest patch within the same minor. Production build verified. Deliberately not taking next@16, which npm proposes: that is a breaking major upgrade with real potential to change rendering and caching behaviour.
Business logic
NONE. Patch-level upgrade; build output verified across all 32 routes.
Status
FIXED — see SEC-016 for the residual advisories that remain.

SEC-007Stored XSS on the unauthenticated receipt page

HighAnonymousFixed
Location
app/api/receipt/[id]/route.ts:138
Vulnerability
The route defines an esc() helper and uses it consistently for names, UTR and rejection reasons — but the customer photo URL was interpolated raw into an attribute: <img src="${photoUrl}" … onerror="…">. A stored value containing a double quote closes the attribute and injects new ones.
Impact
A retailer who can set a customer's photo URL stores script that executes for anyone opening that customer's receipt — and this page is served without authentication, so the payload runs in the browser of customers and staff alike, on the portal's own origin.
Minimal fix
esc(photoUrl) — the helper already present in the file. One call.
Business logic
NONE. Legitimate URLs are unaffected; escaping only alters characters that cannot appear in a valid URL attribute value.
Status
FIXED

Two real defects were found in the fix itself by this process — which is the point of running it.

An unguarded REVOKE on a table absent from two of the three schema baselines aborted the migration's transaction, silently rolling back every fix on those deployments. And re-running the migration would have renamed the newly-installed wrapper to *_impl, producing infinite recursion. Both are fixed and the migration is now confirmed idempotent across three consecutive applies on all three baselines.

Business logic deliberately preserved

Where a security concern touched a business rule, the rule was left alone and the concern reported instead.

  • Customer portal login (SEC-018). /api/customer-login accepts a 10-digit mobile or a 12-digit Aadhaar as the sole credential, and returns the customer's full record including their Aadhaar number. Knowing one customer's mobile number is enough to retrieve their identity documents and full loan history. This is weak authentication by any standard — but it is clearly the product's deliberate design for a no-login customer portal, and tightening it would change how customers reach their accounts. Reported, not changed.
  • Client-supplied payment amounts (SEC-023). /api/payments/submit takes total_emi_amount, fine_amount and total_amount from the request body. A retailer can submit arbitrary figures. The compensating control is the existing workflow: the request is created PENDING and a super admin must approve it. Recomputing amounts server-side would be a change to the payment rules. Reported, not changed — and SEC-001 is what made this genuinely dangerous, since it removed the approval step; with SEC-001 closed the compensating control is real again.
  • Public receipt page (SEC-019). /api/receipt/[id] is intentionally unauthenticated so receipts can be shared with customers. Security rests on the receipt id being an unguessable v4 UUID, and the route already validates the UUID format. Adding auth would break receipt sharing. Reported, not changed.
  • Cross-retailer leaderboard. get_emi_analysis deliberately ranks all retailers against each other. The fix restricts who may call it to the super admin — the only role whose UI renders it — without altering a single figure it returns.
  • EMI sequence enforcement, fine accrual, completion, settlement, NPA. Not touched anywhere. The fine engine, the collection-date gate that decides fine eligibility, partial-payment handling and customer-completion rules are all byte-identical.

Remaining risks & recommendations

Eight open items. None is Critical or High.

Do this first

  • Apply migrations/029_security_hardening.sql to production. Nothing in the database half of this work takes effect until it runs, and SEC-001 stays exploitable until then. It is transactional, idempotent, and verified against all three schema baselines in the repository.
  • Then re-run the suite in tests/security/ against a staging copy to confirm the deployed schema matches what was tested.

Plan next

  • SEC-016 / SEC-017 — dependency upgrades. next@16 and jspdf@4 both fix real advisories and both are breaking. jsPDF in particular generates customer-facing receipts and statements, so an upgrade needs visual comparison of the generated documents before it ships. Schedule these as their own change with QA, not as part of a security patch.
  • SEC-020 — rate limiting. The customer-login limiter is in-memory, so it resets on every cold start and is not shared across serverless instances, and it keys on a client-supplied x-forwarded-for. Move to a shared store (Upstash/Redis) and a trusted client-IP source.
  • SEC-021 — error leakage. Nine routes return raw error.message from PostgREST to the client, which can disclose column and constraint names. Return a generic message and log the detail server-side.
  • SEC-022 — retailer PIN. retail_pin is stored in plaintext, compared with !==, and has no attempt throttling. It only guards a retailer's own actions, so the impact is limited, but hashing it and adding a lockout is cheap.
  • SEC-013 follow-up — CSP. The policy added here covers frame-ancestors, object-src, base-uri and form-action only. Restricting script-src and style-src needs per-request nonces because of the inline theme-boot script and the inline styles used throughout; that is a larger change and was not made blind.

Areas checked and found sound

  • RLS policy design. Policies consistently use get_my_role() and get_my_retailer_id() rather than trusting client input. Cross-tenant reads, cross-tenant inserts, ownership transfer and role self-escalation were all tested and all blocked.
  • Service-role key handling. Confined to lib/supabase/server.ts, imported only by server-side route handlers, never referenced from a client component, and never returned in a response. This is the highest-consequence secret in the system and it is handled correctly.
  • Retailer scoping in the mainstream API routes. /api/metrics, /api/retailer/*, /api/export/*, /api/report/monthly and /api/report/collection all overwrite any client-supplied retailer_id with the value resolved from the caller's own session. This is the correct pattern and it is applied consistently.
  • Backup endpoints. /api/backup uses constant-time comparison, rejects query-string tokens, fails closed when unconfigured, and restricts dumps to a table allowlist. /api/admin/full-backup correctly requires super_admin.
  • SSRF and CORS. No user-controlled server-side fetching — the Google Drive backup path takes its folder id from the environment. No CORS headers are set anywhere, so the browser same-origin policy applies by default, which is the right posture here.
  • XSS elsewhere. lib/loanStatementHtml.ts escapes consistently; the three dangerouslySetInnerHTML uses render locally-constructed strings built from numbers, not stored data.
